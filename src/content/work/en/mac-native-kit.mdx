## Problem

AI can generate SwiftUI and AppKit code quickly, but code that compiles is not necessarily code that remains consistent and maintainable.

In a real macOS project, an AI agent may bypass existing components, recreate native controls, introduce hard-coded styling, or apply web-oriented interface patterns to a desktop application. As the product grows, individual screens can begin to look unrelated, while architectural and platform boundaries gradually break down.

The core problem is not that AI cannot write code. The problem is that AI lacks explicit, enforceable, and verifiable engineering constraints.

## Insight

Natural-language instructions inside a prompt are not sufficient to control the long-term behavior of an AI coding agent.

When component availability, argument types, design tokens, rendering rules, and forbidden implementation patterns are defined as part of the system, interface constraints become executable contracts rather than informal guidance.

The AI should describe interface intent without directly controlling SwiftUI or AppKit implementation details.

## Product Strategy

MacNativeKit is positioned as native macOS UI infrastructure for AI agents rather than as an application-specific component library.

It establishes a controlled boundary between AI-generated intent and native interface code:

```text
AI Agent
→ MacNativeKit DSL
→ Parser
→ Component Schema Validation
→ Native Renderer
→ SwiftUI / AppKit-backed macOS UI
```

The agent can use only registered components. The runtime parses, validates, and renders the declaration, while the consuming application still receives a real native macOS interface.

## Solution

MacNativeKit uses a constrained DSL as the interface declaration layer and is organized around the following system components:

- A DSL lexer, parser, and AST;
- Component schemas and a native component registry;
- Agent prompts generated from registered component schemas;
- Argument count and type validation;
- A native SwiftUI renderer;
- Shared spacing, typography, layout, and control design tokens;
- Platform boundaries for materials and AppKit shells;
- Forbidden-pattern checks and agent development policies;
- A PastePop settings reference implemented with the DSL.

Agents are not allowed to output arbitrary SwiftUI, AppKit, HTML, CSS, JSON UI, unregistered components, or unrestricted platform code.

The current v0.1 release validates the minimum vertical path from a DSL declaration to a rendered native settings interface.

## AI / Technical Approach

The project is implemented with Swift, SwiftUI, AppKit, and Swift Package Manager, with no third-party Swift package dependencies.

The current architecture is divided into focused modules:

- `MacNativeKitLang` parses the constrained DSL;
- `MacNativeKitSchema` defines component and argument contracts;
- `MacNativeKitPrompt` generates agent instructions from registered schemas;
- `MacNativeKitNativeLibrary` registers native macOS components;
- `MacNativeKitRenderer` validates declarations and renders SwiftUI views;
- `MacNativeKitDesign` owns shared design tokens;
- `MacNativeKitMaterial` defines material capability boundaries;
- `MacNativeKitShell` defines window, menu bar, and floating-panel boundaries.

The current native settings component library includes:

- `SettingsScene`
- `SettingsSection`
- `ToggleRow`
- `ButtonRow`
- `PickerRow`
- `SliderRow`
- `TextRow`
- `FooterText`

The prompt generator derives component signatures from the schema registry. A component becomes available to the agent only after it has been explicitly registered.

The renderer does not evaluate arbitrary code and does not generate or inject Swift source. Unknown components, invalid argument types, and missing `root` declarations are rejected or exposed as developer-facing errors.

The current release focuses on structural generation and constraint validation. Two-way application state, action bridges, production window management, menu bar behavior, floating panels, and complete macOS 26 material implementations remain planned work.

## Results

MacNativeKit v0.1 delivers a compilable and testable minimum vertical runtime and validates the following pipeline:

```text
DSL
→ Parser
→ Schema Validation
→ Reference Resolution
→ Native SwiftUI Rendering
```

The PastePop settings reference can be parsed and structurally rendered through the MacNativeKit runtime using registered native settings components.

The repository also includes automated tests and forbidden-pattern checks designed to prevent examples from bypassing the runtime, directly constructing AppKit shells, introducing unauthorized styling, or implementing settings pages outside the declared architecture.

No public user, revenue, or production performance metrics are claimed for the current version.

## Learnings

The central challenge in AI-assisted software development is not only improving the model's ability to generate code. It is also creating system boundaries that the model cannot silently bypass.

A component schema can simultaneously serve as agent documentation, a runtime validation contract, a native rendering entry point, and a source of automated tests. Compared with maintaining a handwritten prompt, this schema-driven approach is more likely to keep the agent's declared capabilities synchronized with the real implementation.

MacNativeKit also validates a broader architectural principle:

> AI does not need to write the interface implementation directly for the final product to contain real, consistent, and maintainable native UI.
