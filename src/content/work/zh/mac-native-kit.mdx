## 问题

AI 可以快速生成 SwiftUI 和 AppKit 代码，但能够编译的代码未必能保持一致并可维护。

在真实的 macOS 项目中，AI 智能体可能绕过已有组件、重新创建原生控件、引入硬编码样式，或将偏向 Web 的界面模式应用于桌面应用。随着产品增长，单个页面可能开始显得彼此无关，而架构与平台边界会逐步瓦解。

核心问题不是 AI 无法编写代码，而是 AI 缺少明确、可强制执行且可验证的工程约束。

## 洞察

提示词中的自然语言指令不足以控制 AI 编程智能体的长期行为。

当组件可用性、参数类型、设计令牌、渲染规则和禁止的实现模式被定义为系统的一部分时，界面约束就成为可执行的契约，而不是非正式的指引。

AI 应当描述界面意图，而不直接控制 SwiftUI 或 AppKit 的实现细节。

## 产品策略

MacNativeKit 被定位为面向 AI 智能体的原生 macOS UI 基础设施，而不是特定应用的组件库。

它在 AI 生成的意图和原生界面代码之间建立受控边界：

```text
AI Agent
→ MacNativeKit DSL
→ Parser
→ Component Schema Validation
→ Native Renderer
→ SwiftUI / AppKit-backed macOS UI
```

智能体只能使用已注册的组件。运行时解析、验证并渲染声明，而使用该系统的应用仍可获得真实的原生 macOS 界面。

## 解决方案

MacNativeKit 使用受约束的 DSL 作为界面声明层，并围绕以下系统组件组织：

- DSL 词法分析器、解析器和 AST；
- 组件模式和原生组件注册表；
- 从已注册组件模式生成的智能体提示词；
- 参数数量和类型验证；
- 原生 SwiftUI 渲染器；
- 共享的间距、排版、布局和控件设计令牌；
- 材质和 AppKit 外壳的平台边界；
- 禁止模式检查和智能体开发策略；
- 使用 DSL 实现的 PastePop 设置参考。

不允许智能体输出任意的 SwiftUI、AppKit、HTML、CSS、JSON UI、未注册的组件或不受限制的平台代码。

当前 v0.1 版本验证了从 DSL 声明到渲染原生设置界面的最小垂直路径。

## AI / 技术方案

该项目使用 Swift、SwiftUI、AppKit 和 Swift Package Manager 实现，且不依赖第三方 Swift Package。

当前架构分为聚焦的模块：

- `MacNativeKitLang` 解析受约束的 DSL；
- `MacNativeKitSchema` 定义组件和参数契约；
- `MacNativeKitPrompt` 从已注册的模式生成智能体指令；
- `MacNativeKitNativeLibrary` 注册原生 macOS 组件；
- `MacNativeKitRenderer` 验证声明并渲染 SwiftUI 视图；
- `MacNativeKitDesign` 维护共享设计令牌；
- `MacNativeKitMaterial` 定义材质能力边界；
- `MacNativeKitShell` 定义窗口、菜单栏和浮动面板的边界。

当前原生设置组件库包括：

- `SettingsScene`
- `SettingsSection`
- `ToggleRow`
- `ButtonRow`
- `PickerRow`
- `SliderRow`
- `TextRow`
- `FooterText`

提示词生成器从模式注册表推导组件签名。组件只有在被明确注册后，才会对智能体可用。

渲染器不会求值任意代码，也不会生成或注入 Swift 源代码。未知组件、无效的参数类型和缺少 `root` 声明会被拒绝，或作为面向开发者的错误呈现。

当前版本聚焦于结构生成和约束验证。双向应用状态、操作桥接、生产级窗口管理、菜单栏行为、浮动面板以及完整的 macOS 26 材质实现仍是计划中的工作。

## 结果

MacNativeKit v0.1 提供了可编译且可测试的最小垂直运行时，并验证了以下流水线：

```text
DSL
→ Parser
→ Schema Validation
→ Reference Resolution
→ Native SwiftUI Rendering
```

PastePop 设置参考可由 MacNativeKit 运行时解析，并使用已注册的原生设置组件进行结构渲染。

该仓库还包括自动化测试和禁止模式检查，旨在防止示例绕过运行时、直接构建 AppKit 外壳、引入未经授权的样式，或在已声明的架构之外实现设置页面。

当前版本不主张任何公开的用户、收入或生产性能指标。

## 收获

AI 辅助软件开发的核心挑战不仅是提升模型生成代码的能力，也在于创建模型无法悄然绕过的系统边界。

组件模式可以同时作为智能体文档、运行时验证契约、原生渲染入口和自动化测试的来源。相较于维护手写提示词，这种模式驱动的方法更有可能让智能体声明的能力与真实实现保持同步。

MacNativeKit 还验证了一项更广泛的架构原则：

> AI 无需直接编写界面实现，最终产品仍能包含真实、一致且可维护的原生 UI。
